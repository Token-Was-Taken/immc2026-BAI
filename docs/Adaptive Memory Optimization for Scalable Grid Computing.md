在内存管理方案中，根据网格规模（Grid Scale）的阶梯式增长，建议采取以下针对性的优化策略，以确保在 **32C32G** 硬件环境下算法的稳定运行。

### 1\. 小规模网格阶段 ($G \< 3,000$)：空间换时间

在此规模下，内存并非瓶颈，应优先追求计算速度。

* **建议方案：** **预计算距离矩阵（Pre-calculated Distance Matrix）** 1。  
* **内存表现：** 存储一个 $O(G^2)$ 的距离矩阵仅需约 **72 MB** 内存（以 3,000 网格计算）1。  
* **优化逻辑：** 将网格间的拓扑距离预先存入内存查表，可使每次适应度评价（Fitness Evaluation）跳过复杂的数学运算，直接获取距离值，从而显著提升 $O(G \\times R)$ 环节的执行效率 1, 2。

### 2\. 中大规模网格阶段 ($3,000 \\le G \\le 10,000$)：监控并发开销

此时 $O(G^2)$ 矩阵的内存占用开始上升，需关注并行处理模式下的内存倍增效应。

* **建议方案：** **共享内存并行（Shared Memory Parallelism）**。  
* **内存表现：** $10,000$ 网格的矩阵占用约 **800 MB**。若使用不具备内存共享机制的多进程并发（如 Python 默认模式），32 个核心会导致内存占用飙升至 **25 GB** 左右，逼近 32GB 的硬件红线。  
* **优化逻辑：** 必须确保所有计算进程共用同一份地图静态数据和距离矩阵，避免冗余副本。若无法实现共享内存，应从该阶段开始切换至**动态坐标计算**。

### 3\. 超大规模网格阶段 ($G \> 10,000$)：强制线性化内存

在此阶段，内存管理成为程序能否运行的决定性因素。

* **建议方案：** **强制动态轴坐标计算（Mandatory Dynamic Axial Calculation）** 1, 3。  
* **内存表现（以 $30,000$ 网格为例）：**  
* **错误做法：** 预存距离矩阵需 **7.2 GB**，在 32 核并发下将瞬间造成内存崩溃。  
* **正确做法：** 仅存储网格的 $(q, r, s)$ 轴坐标，空间复杂度降至 **$O(N \\times G \\times K)$** 1。此时 32 核并发的总内存占用可稳定控制在 **1 GB \- 3 GB** 范围内。  
* **优化逻辑：** 依靠\*\*轴坐标系统（Axial Coordinates）\*\*实现 $O(1)$ 复杂度的实时距离计算 3-5。虽然单次数学运算开销略高于查表，但其极低的内存占用是支持 32 核高并发和 30,000 个决策变量优化的唯一途径。

### 4\. 内存管理通用准则（各规模适用）

* **数据紧凑化：** 使用 **NumPy 向量化运算** 处理所有覆盖模型公式（如公式 8-11）2, 6, 7。这不仅能通过 C 语言底层加速，还能利用更紧凑的连续内存布局降低 Python 对象的内存碎片化开销。  
* **原地修复机制：** 在执行 repair\_solution() 约束修复算子时，应采用 **In-place 修改** 策略 2, 8，直接在原始种群矩阵上更新数据，避免在迭代过程中产生大量的中间解决方案副本。  
* **资源类型控制：** 空间复杂度受资源类型数 $K$ 影响 1。在定义 DeploymentSolution 时，应合理控制可选资源的种类，避免在每一个网格上存储过多的冗余决策变量。
